# 出行方案制作流程

**生成前必读 `references/design-rules.md`**（十条规则：标题与文件名、图片四类规格、跨城交通成章、夜间多选、打卡地一览等），生成后逐条自检。

## 目标产物

一套**自包含、可离线、可分享**的行动方案，通常为两份文件：
- `<方案名>.html`：单文件网页，所有图片以 data URI 内嵌，浏览器可直接打开、可继续编辑。
- `<方案名>.mhtml`：同内容的单文件邮件/微信分享版（用 `scripts/mhtml_pack.py` 生成）。

## 环境自检（开工前由 Agent 完成，不交给用户）

在开始取图/生成前，Agent 先自检依赖并处理，不要求用户手动安装：
1. **Python 3 + Pillow**：运行 `python3 -c "import PIL; print(PIL.__version__)"`。
   - 缺失时先尝试 `python3 -m pip install pillow`；仍失败再明确告知用户具体报错与替代方案（如改用环境已有的图像处理工具）。
2. **浏览器自动化工具**：确认所在平台可用的浏览器工具（WorkBuddy 用 Chrome DevTools CLI，路径见 `pitfalls.md`；其它 Agent 用其自带浏览器工具）。
3. **联网取图能力**：若环境无法联网，明确告知用户，改用 Wikimedia Commons 开放图库兜底，并在方案中如实标注来源。

不要因为依赖未就绪就跳过素材步骤或假装完成。

配套可选：`<方案名>_路线地图.html`——基于腾讯地图 JS API GL 的可交互地图页（需联网），支持按钮切换线路、缩放、点选地点。

## 制作流程（按顺序）

### 1. 需求采集

**生成前先向用户确认以下三项**（可一次性问，用户答不上来就按目的地特点给建议并标注假设）：
1. **住宿倾向**：片区（如天河/珠江新城）+ 价位区间（如 ¥400–700/晚）。
2. **餐厅倾向**：菜系（粤菜/潮汕菜/客家菜等）+ 人均价格区间（如 ¥100–150）。
3. **喜欢逛的景点**：类型或具体点（地标/博物馆/老城街巷/自然风光），可让用户报几个名字。

另确认：出行主题与日期、人数与构成（如两地同学）、集合点、每日主线与备选、是否有主题诗/标语等个性化内容。
- 需求不全时先做合理假设并在方案中标注"待确认"，不要停下来反复追问。

**生成时把答案落到具体选择**：住宿片区决定选哪家酒店、价位决定候选档位；餐厅菜系与人均决定首推餐馆；喜欢的景点类型决定每日景点与两条备选路线。
- **热点事件**：确认用户是否指定城市当期热点（如会议、赛事、节庆）；未指定则主动搜索出行日期前后的热点。融入方法见 `references/hotspots.md`。

### 2. 素材准备
- 从内容平台搜集真实素材：餐厅/景点实拍优先小红书，餐厅评价与人均用大众点评，酒店价格与实拍用携程、飞猪交叉核验。**具体平台操作、登录态、URL 格式与坑见 `references/sourcing.md`。**
- 收集照片，按场景分组（每个场地：1 张大图 + 3 张小图效果最佳）。
- 用 `scripts/normalize_images.py` 统一比例：大图约 22:10、小图 16:9，采用**模糊填充保留完整画面**，绝不硬裁。
- 把图片转为 data URI 内嵌进 HTML（`--data-uri`），保证离线可用。
- 图片必须自包含：任何外链图片在离线/转发场景下都会丢失。

### 3. 生成 HTML 方案
以 `assets/plan-template.html` 为骨架，替换 `{{占位符}}`，并按下方组件规范填充各 section。

### 4. 路线地图（可选但推荐）
按 `references/map.md` 生成独立地图页，再截图嵌入方案的 `routemap` 章节。

### 5. 打包与验证
- 运行 `scripts/mhtml_pack.py` 生成 MHTML。
- 用浏览器打开 HTML 做结构验证（见 `references/pitfalls.md` 的验证清单）。
- 通过后用文件展示工具呈现两份文件。

## Section 组件规范

所有 section 统一结构：

```html
<section id="xxx">
  <div class="sec-h"><span class="no">序号/图标</span><h2>中文标题</h2><span class="en">ENGLISH</span></div>
  <div class="card"> ... </div>
</section>
```

常用组件与用途：
| 组件 | class | 用途 |
|---|---|---|
| 键值行 | `kv` > `k` + `v` | 天气穿衣、亮点/交通/话题等成组说明 |
| 图片组 | `pics` > `hero-pic` + `thumbs` | 1 大 + 3 小图，figcaption 写图注 |
| 时间轴 | `tl` > `ev` > `t`(`time`/`name`/`dur`) + `p` + `line`/`chips` | 行程时间线 |
| 说明行 | `line` > `lab` + 文本 | "看点/话题/交通/返程"等带标签的小段 |
| 提示块 | `note` / `note blue|green|warn` | 提醒、加分项、警告 |
| 路线卡 | `route a|b` > `top` + `body` | 次日双路线 |
| 图例 | `maplegend` | 地图编号对照 |
| 表格 | `tblwrap` > `table.overview|compare` | 全程一览、对比表 |

## 内容组织原则

- **语气**：口语化、亲切、有画面感；避免公文腔。同一批文案保持人称与措辞一致。资料面向全体同学，用第三人称/中性口吻，不用指导口吻（详见 `references/collaboration.md`）。
- 主题诗、标语、温馨提示与一览表的写法见 `references/content.md`。
- **可选 vs 必选**：所有非核心安排明确标注"可选/自愿参加/视时间而定"，且标注位置统一（如时间列）。
- **地名/人名强调规则**（贯穿全文，务必一致）：
  - APEC/名人打卡地的**人名与地名**：加粗绿色 `.apec`（浅色 `#0a8a5a`、深色 `#4fd08a`）。
  - 非打卡地的场所/店名（餐厅、商场、基地）：加粗蓝色 `.venue`（浅色 `#12507e`、深色 `#79b8f0`），避免与打卡地混淆。
  - 不要把普通地名一律加绿；判断是否"打卡地"后再选样式。
- **笼统表述要补具体**：如"XX 同款"应写明是谁（含职务），不要只写"总理同款/某某同款"。
- **时间一致性**：多条可选路线的时间段应统一（如都是 09:00–12:30）；具体午餐时刻可保留差异。

## 字号与排版

- 桌面端（≥720px）统一放大正文：body 21px、正文段 20px、卡片标题 23px、章节标题 25px（模板 CSS 已含）。
- 开头 header 与主题诗居中；其余左对齐。
- 内容区宽度用 `.wrap{max-width:none}` 全宽，避免大屏两侧大片空白。
- 图注、标签等小字不要低于 12px；编号字号与相邻文字一致。

## 填入 header / poem 占位符（易错点）

模板 poem 区的四个占位符要按实际结构填，不要猜正则：
- `{{POEM_VERSE_HTML}}`：填**若干 `<p>诗句</p>`**（七律通常 4 句），不是纯文本。
- `{{POEM_NOTE}}`：填一段白话解题文本。
- `{{SLOGAN1}}`–`{{SLOGAN4}}`：填 4 枚短标语文字（不含 `<span>`，模板已包）。
- `{{POEM_LABEL}}`：填小标（如"羊城一别 · 鹏城聚首"）。

从已有 HTML 提取时， poem 的三个子元素（`.verse`/`.poem-note`/`.slogan`）都是**单层 div**，不要用三层嵌套的正则去匹配；`data-page-node-id` 属性要先剥掉。生成后务必浏览器验证 `poem.querySelectorAll('.verse p').length` 与标语数，防止诗句/标语为空却看不出来。

## 交互脚本（模板已内置，勿删）

`assets/plan-template.html` 的 `<script>` 含三项必备交互，生成方案时保留：
1. **图片放大** `zoom(el)`：点图全屏查看，配 `#zoom` 遮罩。
2. **导航滚动高亮**：用 `IntersectionObserver` 观察各 section，滚动时高亮对应 nav 链接（`rootMargin:'-30% 0px -65% 0px'`）。
3. **主题切换**：默认跟随系统 `prefers-color-scheme`，右下角按钮手动覆盖并用 `localStorage` 记忆；`data-theme` 属性优先于系统设置。

验证时检查 `document.querySelector('script').innerText` 是否含 `IntersectionObserver` 与 `themeToggle`，缺失会导致导航无高亮、主题按钮失效。

## 迭代修改原则

用户会对文案与排版反复微调。修改时：
1. **只改指定处**，保持无关内容与既有结构不变。
2. 用文本精确替换（带唯一上下文），改完立即用浏览器验证 DOM 结构与视觉。
3. 每次改动后**同步重新生成 MHTML**，避免两份文件不一致。
4. 用户说"没效果/不明显"时，先用浏览器测量实际 DOM（宽度、颜色、行数、父元素链）定位根因，不要盲目再调数值。
